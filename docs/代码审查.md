## 一、这次修掉的（都进了 2.10.32）

### 内存安全 / 崩溃
| # | 位置 | 问题 | 修法 |
|---|------|------|------|
| ✅1 | `mirisdrdevice.c` openAsync | mode 回退到静态数组后，仍把这个指针交给 `ReleaseStringUTFChars` —— 违反 JNI 规范（未定义行为，偶发闪退）；jstring 为 NULL / OOM 也没兜住 | 另存 `GetStringUTFChars` 的原始指针再释放；NULL 一律给空串/默认值 |
| ✅2 | `librtlsdr.c` rtlsdr_open2 | `libusb_open2` 返回值没检查，失败时 `dev->devh == NULL` 却被 `libusb_kernel_driver_active` 解引用 → 空指针崩溃（上游有 `r<0 goto err`，移植时漏了） | 判 `r<0 || devh==NULL` 就 goto err；失败时关掉 dup 的 fd |
| ✅3 | `libusb/core.c` `libusb_open2` | 漏了 `auto_detach_kernel_driver = 0`（上游 `libusb_open` 里有）→ claim 时读未初始化内存，可能多做一次内核驱动摘除 | 补上该初始化 |
| ✅4 | `Log.java` appendLine | 空串 / 只有换行的串：`charAt(length-1)` → `StringIndexOutOfBoundsException`，且这是在 native 调用的线程上（@UsedByJni） | 循环加 `what.length() > 0` |
| ✅5 | `AsyncFuture.get()` | 只 `wait()`、不判 `ready`：授权广播若先到，等待方永远不醒（USB 授权流程永久卡住） | `while(!ready)` + 带超时版抛 TimeoutException |
| ✅6 | `MainActivity` 全部弹窗 | 长任务（首次初始化 10~30s、USB 自检数秒）的回调里 `main.post { …show() }`：onDestroy 的 `removeCallbacksAndMessages` 只能清已入队的，之后入队的弹窗会因 window token 失效抛 `BadTokenException` 闪退 | 新增 `Builder.showSafe()/AlertDialog.showSafe()`，**40 处全部收口**（销毁就不弹） |

### 资源泄漏 / 卡死 / 白耗电
| # | 位置 | 问题 | 修法 |
|---|------|------|------|
| ✅7 | `sdrtcp.c`（**两份拷贝**） | `client_socket` 只置 -1、**从不 close** → 每服务完一个客户端泄漏一个 fd，"客户端一走就重启"的设计下反复连接最终 EMFILE，内置驱动再也起不来 | `cleanup` 里 `shutdown+close` |
| ✅8 | `sdrtcp.c`（两份） | `recv()==0`（对端半关）只判 `-1`：被判为"没数据"，select 一直可读 → 命令线程 **100% CPU 空转**（发热/掉电） | `received<=0` 一律当 EOF 收尾 |
| ✅9 | `sdrtcp.c`（两份，共 4 处） | `sdrtcp_feed` 在"客户端没就绪"分支 `usleep(500ms)` —— 它是**在 libusb 完成回调里**被调用的，等于每个 IQ 块按住事件循环半秒（启动慢/取消慢/丢包）。文件自己的注释就写着"绝对不能等" | 直接丢弃该块，不等待 |
| ✅10 | `sdrtcp.c`（两份）+ 头文件 | 服务线程 `JOINABLE` 却句柄是局部变量、**永远没人 join**（每轮连接泄漏线程栈）；`sdrtcp_free` 只 `pthread_mutex_destroy` 就返回，线程可能还在用它正在用的结构（use-after-free） | 线程改 DETACHED；新增 `worker_done` 标志（closedcb 之后置位），`sdrtcp_free` 先停、再等 ≤2.5s 才销毁 |
| ✅11 | `libusb_compat.c` | `dup()` 出来的 fd 在 `libusb_open2` 失败时没人关（open2 失败路径不接管 fd）→ 反复失败最终 fd 耗尽 | 失败时 `close(myfd)` |
| ✅12 | `libmirisdr.c` | `libusb_wrap_sys_device` 失败只 `free(dev)`，漏 `libusb_exit` → 每次失败泄漏一个 context | 补 `libusb_exit` |
| ✅13 | `librtlsdr.c` + `RtlSdrDevice.java` | Java 侧把 `UsbDeviceConnection` 交给 GC，而 libusb 直接 close 同一个裸 fd：① 连接被回收 → 传输中 fd 被关、流随机断；② libusb 先关 → fd 号被复用后再关一次就关了**别人**的 fd | native `dup` 一份 fd（与 Mirics 模块同做法）；Java 侧长期持有连接 |
| ✅14 | `librtlsdr.c` | EEPROM 读失败没检查，用未初始化栈缓冲判机型/强制偏置供电，还会按垃圾长度越界读 | 失败即 `memset(buf,0)` 并跳过判断 |

## 三、查过、**确认没问题**的点（避免重复排查）

1. **JSON 契约**：`lbj_radio.snapshot()/autocal_state()/calib_state()/scan` 与 `lbj_engine` 的键，逐一对照 Kotlin 读取端，无缺键、无类型不符（"缺键"的告警全是我脚本的误报）。
2. **SharedPreferences 键**：无"只读未写"（拼写错误）也无"只写未读"的孤立键。
3. **`String.format` 类型**：Kotlin/Java 逐条核对，格式符与实参类型全部匹配；历史崩溃点（历史详情）已用 `s()/d()` 规避 `JSONObject.NULL`。
4. **协议单位**：`SET_GAIN` 0.1dB ↔ Mirics 整数 dB（`(p+5)/10`）、`sdrtcp_feed` 长度=16 位元素个数（mirisdr 3 处 + RTL 1 处全部 `/2`）、`rtlsdr_set_tuner_gain` 收 tenths —— 均一致。
5. **504 帧重组边界**：`frame_buf[4096]` 的 memcpy/memmove 长度、对齐搜索上限（≤2051）、BULK 输出缓冲恰好 16128 字节（`(16384+1023)/1024×1008`）都算过，不越界。
6. **硬编码数组上限**：增益档位走 `miri_get_gains(cap=128)`（103 个不再溢栈）、网格/日志数组边界都有守卫。
7. **JNI 面**：Mirics 11 个、RTL 5 个 Java native 与 C 入口一一对应；`GetMethodID` 失败有 `ExceptionClear`。
8. **USB 过滤表 ↔ Mirics 识别表**：7 条 Mirics ID 与 `MIRI_KNOWN` 一致。
9. **许可证**：vendored 的 libmirisdr / librtlsdr / libusb / sdrdrive 相关文件**全部带 "or later"**（GPL-2.0-or-later / LGPL-2.1-or-later），与项目 GPL-3.0-or-later 兼容。
10. **打包/签名**：密钥与 `local.properties` 都不进仓库（缺失时退回 debug 签名，别人也能构建）；`abiFilters arm64-v8a` 与 Chaquopy 17 的运行时一致。
11. **无遗留 TODO/FIXME**；`onDestroy` 的 `removeCallbacksAndMessages(null)` 确实能清已入队的延迟任务。
12. **两份 `sdrtcp.c` 除注释外逐字节相同**（不存在"一份改了一份没改"）。

# 补修（v2.10.34：把上一节"未修"里能做的都做了）

## native（两个驱动模块）
- ✅ Mirics-H1 **use-after-free**：`mirisdr_close()` 等到的 INACTIVE 是在读线程做 `mirisdr_async_free/streaming_stop` **之前**置的 → 新增 `reader_done` 标志，读线程彻底收尾后才置位，`mirisdr_cancel_async_now()` 有界等待（≤2s）它之后再释放。
- ✅ Mirics-H3 `announceOnOpen`/streaming 顺序：原来写在**阻塞的** `mirisdr_read_async` 之后（等于"流结束了才回调/才标记在跑"）→ 提前到读循环之前；读循环返回后主动收尾（关设备 + 收监听端口）。
- ✅ Mirics-M5 竞态：`miri_closed_cb/miri_command_cb` 改持 `d->lock` 读 `d->dev`（releaseUsb 是"先 close 再置 NULL"，无锁读会摸到已释放指针）。
- ✅ Mirics-M12 err 路径顺序：先置 `d->dev=NULL` 再 close；并等监听端口真的关掉（否则马上重试会因 state 未复位而失败）。
- ✅ Mirics-M11 `samples_realloc`：只在 malloc 成功后才更新 `samples_size`（原来失败也更新且丢掉旧缓冲 → 调用方拿 NULL 当 dst 崩）。
- ✅ Mirics-M1 抽取：只实现了 1×/2×，对 k≥3 的请求原来"设了不抽"（客户端拿到 k 倍速率）→ 就近吸附到 650k×2，并明确日志。
- ✅ Mirics-M2 自检"带宽对比"传的是**枚举**而函数收 **Hz**（7/3 都 ≤200000 → 两次都是 200kHz）→ 改传 8000000/1536000。**此前"带宽宽窄无差别"的结论作废**。
- ✅ Mirics-M7：PPM 在 Mirics 侧是空实现 —— 自检报告里明写"PPM 未实现"，不再让用户以为调了有用。
- ✅ Mirics-L5/L6：`FindClass/NewObjectArray` 判空；看门狗线程创建失败就跳过本次真收数据测试（否则设备不给数据会把自检永久卡住）。
- ✅ sdrtcp-M5 状态机竞态：`sdrtcp_stop_serving_client` 的 state 读改写全部持 `state_locker`（与 tcp_server 置 SERVING 竞争会导致 workpool 已 free 仍进 serveClient → 100% CPU 死循环且服务线程退不出）。两份拷贝同步。
- ✅ RTL-H2/H3：关闭顺序改为"先停服务线程并等 `worker_done`，再置 `rtl_dev=NULL`，再 close 设备"（原来先 close 再停 → 命令线程可能拿着已释放的 `rtlsdr_dev_t` 调 librtlsdr）。
- ✅ RTL 日志：`%ld`/`%dl` 配 `uint32_t`（arm64 上打印随机高位）全部改成 `%u` 并加显式 cast。
- ✅ CMake：`SET(CMAKE_C_FLAGS "-Wall")` 是**覆盖**，会丢掉 toolchain 的 `-fstack-protector-strong` 等加固 flags → 改成追加（编译日志已确认加固 flags 回来了）。
